## What Works

2026-06-20 — `ContainerOverrides` is the correct test-double injection point for all adapters — pass mocks via `new Container(config, db, { llm: { openai: new MockLLMProvider() }, github: new MockGitHubClient() })`. Using `vi.mock()` on an adapter module file is a code smell here: if you need it, the dependency should be constructor-injected instead. ref: server/src/adapters/mocks.ts:1

2026-06-21 — `safeFetchSkillUrl` streams the response body to enforce the 100KB limit without buffering the full payload: `reader.cancel()` is called once the running total exceeds `MAX_BYTES`. Using `res.arrayBuffer()` would let an oversized payload into memory before the check. The streaming approach is the correct pattern for size-guarded fetches. ref: server/src/modules/skills/routes.ts:65

2026-06-21 — Conventions extractor verifies LLM-returned evidence before accepting candidates: `verifyEvidence()` reads the file at `evidence_path` and checks that the first line of `evidence_snippet` literally appears in its content. LLM hallucinated file paths or invented snippets silently fail this check and are dropped. No verification = hallucinated conventions reach the DB. ref: server/src/modules/conventions/extractor.ts:35

2026-06-18 — Unit-testing a drizzle repo function with two sequential queries: mock `db.select()` with a call counter; each call returns a fresh chain where `.orderBy()` (first query) or `.groupBy()` (second query) resolves with the appropriate fixture data. All intermediate chain methods (`from`, `leftJoin`, `innerJoin`, `where`) return `this`. Pattern validated for `listRunsForPull`. ref: server/src/modules/reviews/repository/run.repo.severity.test.ts:53

## What Doesn't Work

2026-07-05 — A prior in-progress implementation of `resolveFeatureModelStrict` (feature-model strict-resolution retrofit) reintroduced the exact silent-fallback bug the retrofit was meant to remove: it checked `getFeatureModelOverride` first, but if `undefined`, fell back to `FEATURE_MODELS.find(f => f.id === id)`'s `defaultProvider`/`defaultModel` before throwing — since every registry entry has both fields set, the function could never actually throw in practice. Caught only because the pre-written unit tests in `feature-models.test.ts` already asserted the correct (throw-always) behavior and failed against the buggy implementation. Lesson: when a "strict" function still reads from the same registry the old lenient one used, verify by deleting the registry-lookup line entirely, not just renaming the wrapper. ref: server/src/modules/settings/feature-models.ts:48

2026-07-05 — The global `@fastify/rate-limit` plugin is deliberately NOT registered when `config.nodeEnv === 'test'` (`app.ts:95-97`, comment: "so integration suites can hammer endpoints via inject()"). Consequence: a route's own `config: { rateLimit: {...} }` override has ZERO effect under `NODE_ENV=test` too, since `@fastify/rate-limit` must be globally registered for Fastify to even interpret per-route `config.rateLimit`. To integration-test a 429 path (e.g. onboarding/brief's `{max:10,timeWindow:"1 minute"}`), build that ONE test's app with `loadConfig({...process.env, NODE_ENV:'development'})` instead of `'test'` — everything else (real Postgres via testcontainers, mock adapters) still works identically. ref: server/src/app.ts:93

2026-07-05 — Onboarding's structured LLM output includes top-level scalar metadata fields (`repoName`, `filesIndexed`, `generatedAt`, `headSha`) alongside the 5 narrative sections — these were echoed straight from `result.data` (the LLM's raw response) with no server-side overwrite, unlike the already-guarded `sections.howToRun`/`firstTasks`/`readingPath`. Consequence in production: the model has no real notion of wall-clock time and returned a `generatedAt` far in the past, so a just-generated tour displayed "last refreshed 452 days ago." Fix: overwrite ALL top-level metadata unconditionally right after grounding, same pattern as the section-level overwrites — "mechanical/server-known field" guards must be applied per-field, not just per-section; it's easy to fix the sections and forget the top-level scalars sitting next to them in the same schema. ref: server/src/modules/onboarding/service.ts:252

2026-07-07 — `AgentsRepository.insert()`/`SkillsRepository.insert()` never supply `repo_id`, even though migration `0015_mushy_carlie_cooper.sql` made `agents.repo_id`/`skills.repo_id` NOT NULL (migration `0014` added the columns nullable; `0015` tightened them, but `InsertAgent`/`InsertSkill` + `CreateAgentBody`/`CreateSkillBody` were never updated to accept/require one). Result: `POST /agents` and `POST /skills` throw a 500 ("null value in column repo_id... violates not-null constraint") on literally every call — this is NOT a regression from any eval-pipeline work; confirmed pre-existing at the exact session-start commit via a throwaway `git worktree add <sha> --detach` + `pnpm typecheck`, and it independently breaks the PRE-EXISTING `test/reviews.it.test.ts` ("agents CRUD", "runs a review") and `test/skills.it.test.ts` suites too. Workaround for eval-pipeline integration tests: seed `agents`/`skills` rows directly via `db.insert(t.agents).values({..., repoId})` (and hand-insert the matching `agent_versions`/version-1 snapshot row, since bypassing the repository skips `snapshotVersion()`) rather than going through `POST /agents`/`POST /skills`. `PUT /agents/:id` and `GET /agents/:id/versions` etc. all work fine — only the two INSERT paths are broken. ref: server/src/modules/agents/repository.ts:86

2026-07-05 — Retrofit-completeness grep must cover `server/test/` in addition to `server/src/` — `grep -rn "resolveFeatureModel\b" server/src` reported zero matches (true for src), but `server/test/settings-models.it.test.ts` still imported the deleted `resolveFeatureModel` and would have failed to even compile/run. Always widen a "no more references" grep to the whole package root, not just the primary source tree. ref: server/test/settings-models.it.test.ts:9

2026-06-17 — `selectDistinctOn([agentRuns.prId])` for cost silently returns null when the most recent run errored (`cost_usd = null`). DISTINCT ON picks the newest row regardless of whether the value is null — so a trailing error run zeros out the entire COST column. Fix: use `sql\`sum(${t.agentRuns.costUsd})\`` with `.groupBy(t.agentRuns.prId)` — SQL SUM skips nulls, so error runs don't affect the total. ref: server/src/modules/pulls/routes.ts:122

2026-07-07 — Drizzle `.select({...}).from(...).groupBy(...).as('alias')` can be used as a subquery in a subsequent `.leftJoin()`, letting TWO independently-grouped aggregates (each avoiding fan-out from the other's join) combine into ONE round-trip query. Used for `AgentsRepository.statsForWorkspace()`: one subquery aggregates `agent_runs` (runs_count, avg cost), a second aggregates `findings JOIN reviews` (accept rate), both LEFT JOINed onto `agents` in the outer query — avoids the fan-out corruption a single flat JOIN across all three tables would cause (a run with 5 findings would 5x-count its own cost in a naive combined AVG). No prior usage of drizzle subqueries existed anywhere else in this codebase before this. ref: server/src/modules/agents/repository.ts:280

## Codebase Patterns

2026-06-21 — Fastify route registration order: `/skills/import` and `/skills/:id/stats|versions|restore` MUST be registered before `/skills/:id`. Fastify matches literal path segments first only if they are registered first — "import" otherwise binds as a UUID param and returns 404. Documented in a NOTE comment at the top of `skillsRoutes`. ref: server/src/modules/skills/routes.ts:27

2026-06-21 — `SkillsRepository.update()` only bumps `version` when `body` actually changes (new value !== existing). Metadata changes (name, description, enabled, type) are NOT versioned. A body change also resets `threat_level` to `"unknown"` so the synchronous re-scan on `PUT /skills/:id` starts from a clean slate. ref: server/src/modules/skills/repository.ts:154

2026-06-29 — A new module's service must NOT do direct Drizzle queries (`container.db.select()`) — all DB access belongs in a dedicated `repository.ts`. This is an Onion Architecture enforcement: Application layer (service.ts) must not depend on Infrastructure (Drizzle). Pattern: `this.repo = new BlastRepository(container.db)` in the service constructor; all `db.*` calls live in `repository.ts`. Architecture reviewer catches this as a HIGH violation. ref: server/src/modules/blast/service.ts:1

2026-06-29 — Two parallel type hierarchies exist for blast radius data: `server/src/modules/repo-intel/types.ts` has internal types (`ChangedSymbol`, `BlastCaller`) used within repo-intel; `server/src/vendor/shared/contracts/brief.ts` has the HTTP contract types (`BlastChangedSymbol`, `BlastCallerRow`, `BlastRadiusResult`). These are structurally compatible but distinct — the prefix `Blast` was added to shared types to avoid name collision. Never merge them; the internal types can evolve independently of the HTTP contract. ref: server/src/vendor/shared/contracts/brief.ts:1

2026-07-03 — `pr_brief` table (`{prId PK, json jsonb}`) has no `headSha` column, unlike `pr_intent` which reuses `pull.lastReviewedSha` for cache invalidation. Any feature that caches per-PR LLM output and needs to invalidate on new commits (e.g. the Why+Risk Brief feature, SPEC-2026-07-03-pr-why-risk-brief) must add a `headSha` column to the cache table first — copying the `pr_intent` invalidation pattern (`cachedHeadSha !== pull.headSha`) does not work out of the box against `pr_brief`'s current schema. ref: server/src/db/schema/reviews.ts:75

2026-06-21 — Scan strategy differs by route: `PUT /skills/:id` runs regex + LLM scan **synchronously** so the response body contains the final `threat_level`. `POST /skills/import-url` runs regex synchronously (result goes into DB immediately) then fires LLM scan **in background** after `reply.status(201)` is sent — the background result upgrades the DB row asynchronously. ref: server/src/modules/skills/routes.ts:140

2026-06-21 — Threat level is never downgraded from `"dangerous"`. LLM scan result is applied via a severity map `{ safe:0, unknown:1, suspicious:2, dangerous:3 }` — it replaces the current level only when its numeric rank is strictly higher. A `DANGEROUS` regex result cannot be softened by a `safe` LLM result. ref: server/src/modules/skills/routes.ts:272

2026-06-21 — Skills from untrusted sources (`imported_url`, `community`) are wrapped in `<untrusted source="skill:…"> … </untrusted>` delimiters before injection into the review prompt. The skill body's own `</untrusted>` tags are escaped to prevent breakout. Manual and extracted skills pass through unwrapped (trusted). ref: server/src/modules/reviews/run-executor.ts:244

2026-07-07 — The untrusted-skill-body wrapping guard (`imported_url`/`community` sources) is NOT specific to the `skills: string[]` parameter of `reviewPullRequest` — it must be applied ANYWHERE a skill body reaches a prompt, including when concatenated directly into `systemPrompt` (as the eval module's skill-eval path does per spec: `` `${REFERENCE_PROMPT}\n\n${skill.body}` ``). The spec's literal string construction didn't mention the guard; applying it anyway (mirroring `run-executor.ts`'s exact wrap logic in a small `wrapSkillBodyIfUntrusted` helper) is required by reviewer-core's own stated rule ("never concatenate untrusted content directly into the system prompt") — a plan omission, not a plan requirement to skip it. ref: server/src/modules/evals/service.ts:291

2026-07-07 — `agent_versions.config_json` (jsonb) is the ONLY place a historical `system_prompt` value survives — `agents.system_prompt` only ever holds the CURRENT value. Any feature needing an OLD version's prompt text (e.g. `GET /agents/:id/versions` for a prompt diff view) must read it back out of `config_json.system_prompt`, not the live `agents` row. Mirrors `SkillsRepository.listVersions()`'s pattern exactly (skills store the historical `body` as its own dedicated column on `skill_versions`, though — agents don't have a dedicated historical column, only the jsonb snapshot). ref: server/src/modules/agents/repository.ts:158

2026-06-21 — `PATCH /repos/:repoId/conventions/:id` is a polymorphic endpoint: `{ rule: string }` → inline edit; `{ accepted: true }` → accept; `{ accepted: false }` → reject + delete; both absent → `ValidationError`. `rule` takes priority if present alongside `accepted`. ref: server/src/modules/conventions/routes.ts:57

2026-06-20 — Layer mapping for Onion Architecture: Domain=`src/vendor/shared/contracts/` (pure TS types, zero framework imports), Application=`modules/*/service.ts` (orchestration, no SQL), Infrastructure=`modules/*/repository.ts` + `src/adapters/` (Drizzle, Octokit, OpenAI SDK), Presentation=`modules/*/routes.ts` (Fastify handlers). Documented in `.claude/skills/onion-architecture/`. ref: server/src/platform/container.ts:1

2026-06-20 — `src/platform/` is NOT an architectural layer — it is cross-cutting infrastructure (Container, RunBus, JobRunner, AppError, AppConfig) that any layer may import without violating the inward-only dependency rule. Treating it as a layer and avoiding imports from it is a mistake. ref: server/src/platform/container.ts:1

2026-06-20 — Cross-module data access: a service must never import another module's `repository.ts` directly. Instead, shared repositories are pre-built as properties on `Container` (e.g. `container.agentsRepo`). To add cross-module data access, add a property to `Container` first, then use it via `this.container.X`. ref: server/src/platform/container.ts:1

2026-07-02 — `reposRepo` lazy getter added to Container following the `agentsRepo`/`skillsRepo`/`reviewRepo` pattern (private `_reposRepo?`, `get reposRepo()` returning `new RepoRepository(this.db)`). Services needing cross-module repo access (`ContextService`) inject `Container` via constructor (type-only import to avoid circular dep), then call `this.container.reposRepo`. Route handlers stay thin — no infrastructure instantiation in `routes.ts`. ref: server/src/platform/container.ts:113

2026-07-05 — Architecture decision: a drill-down sub-diagram (`buildSubDiagram` in onboarding's `service.ts`) is only generated when there are ≥2 real files AND ≥1 real connecting edge between them (from `getCriticalPaths` chains, restricted to pairs both present in the candidate set) — otherwise it returns `null` and the client shows an honest "no detail available" message. Rationale: a single box, or several disconnected boxes with no lines, isn't an "architecture" — it's just restating a file name/list with extra visual ceremony, and a user reported it as confusing/broken-looking. Chose "no diagram" over "diagram with 1 box" deliberately — same philosophy as the rest of onboarding's grounding gate (honest gaps beat fabricated/low-value content). ref: server/src/modules/onboarding/service.ts:529

2026-06-20 — `getContext(container, req)` is the mandatory first call in every Fastify route handler — it extracts `workspaceId` + `userId` from the auth context. Never read `workspaceId` from `req.headers` manually in a handler; always go through `getContext`. ref: server/src/modules/_shared/context.ts:1

2026-06-18 — `agent_runs` stores only total `findingsCount` and `blockers` — no per-severity breakdown. To get critical/warning/suggestion counts per run, use: `findings` JOIN `reviews` (on `reviews.id = findings.reviewId`), filter `inArray(t.reviews.runId, runIds)`, group by `(reviews.runId, findings.severity)`. Second query pattern, merge into result map. ref: server/src/modules/reviews/repository/run.repo.ts:51

2026-06-17 — `nullish()` (not `nullable()` or `optional()`) is the convention for optional DTO fields in `platform.ts`. Use `z.number().nullish()` for fields that may be absent from older DB rows — accepts both `null` and `undefined` from Drizzle. ref: server/src/vendor/shared/contracts/platform.ts:157

2026-07-12 — The multi-agent contracts in `observability.ts` (`AgentColumnFinding`, `AgentColumn`, `ConflictTake`, `Conflict`, `MultiAgentRun`) are fully defined but UNUSED — documented as the responses of `POST /pulls/:id/multi-agent-run` + `GET /pulls/:id/multi-agent`, which don't exist yet. `MultiAgentRun` (line 75) has `pr_number` but NO `pr_title`, so any detail page needing a PR-title line must extend the contract (SPEC-2026-07-12-multi-agent-review adds `pr_title`). Note `AgentStats`/`GET /agents/:id/stats` in the SAME file belongs to a SEPARATE future "Agent Performance" feature — target the multi-agent ones, leave `AgentStats` alone. ref: server/src/vendor/shared/contracts/observability.ts:75

2026-07-12 — `multiAgentRuns` table (`db/schema/runs.ts:42-51`) exists but has ZERO linking columns and is never read/written anywhere — it's a stub. Linking `agent_runs` to a multi-agent batch requires a NEW migration adding a nullable `multiAgentRunId` FK on `agentRuns` (`onDelete: 'set null'`); the batch table alone can't associate runs. ref: server/src/db/schema/runs.ts:42

2026-07-12 — For a per-agent duration/cost estimate (multi-agent picker/Configure-run), the settled design EXTENDS `AgentsRepository.statsForWorkspace` with one new aggregate field (`avg_duration_ms` alongside the existing `avg_cost_usd`), exposed on the `Agent` contract via the existing `GET /agents` — deliberately chosen OVER a duplicate reviews-module-owned `avg(durationMs)` query. Rationale: two independent "average per agent" calculations could silently drift if the aggregation logic changes in only one place. One-source-of-truth wins even though it means a narrow, cross-feature edit into `agents/repository.ts`. ref: server/src/modules/agents/repository.ts:334

## Tool & Library Notes

2026-07-05 — The onboarding system prompt described `architecture.edges[]` as merely present ("directed edges between node ids"), not required — a real generation returned 5-7 valid nodes with a completely EMPTY edges array, rendering as disconnected floating boxes with no visual relationships (looked broken, not "sparse"). LLMs (DeepSeek in this case) treat optional-sounding schema fields as skippable under any ambiguity. Fix: state the requirement as a hard rule with an explicit minimum ("for 2+ nodes, return at least (nodes.length - 1) edges") rather than describing the field's shape alone. Also: don't ask the model to also fill an optional `detail` field the server discards anyway (see grounding pattern below) — every extra optional field is attention the model might spend instead of getting the required ones right. ref: server/src/prompts/onboarding.system.md:12

2026-06-17 — `sql` template tag from `drizzle-orm` is NOT included in the common named-export bundle used in this file (`and, desc, eq, inArray`). When adding raw SQL expressions (e.g. `sql\`sum(...)\``), add `sql` to the import explicitly: `import { and, desc, eq, inArray, sql } from 'drizzle-orm'`. Missing it gives a "sql is not defined" runtime error, not a TS error. ref: server/src/modules/pulls/routes.ts:3

2026-06-17 — Drizzle `selectDistinctOn([col])` requires the first `orderBy()` column to match the DISTINCT ON column. For "latest row per group": `.selectDistinctOn([t.agentRuns.prId], {...}).orderBy(t.agentRuns.prId, desc(t.agentRuns.ranAt))`. Without the matching prId in orderBy, Postgres throws "SELECT DISTINCT ON expressions must match initial ORDER BY expressions". ref: server/src/modules/pulls/routes.ts:1

2026-07-07 — `MockLLMProvider` (`src/adapters/mocks.ts`) returns the SAME `structured`/`structuredBySchema` fixture on EVERY `completeStructured` call, regardless of what diff/messages were sent — it cannot vary its response per-call based on input content. For a test needing per-call-varying output driven by THIS call's diff (e.g. asserting two different "Run all evals" batches produce different recall/precision after a prompt edit), write a small custom `LLMProvider` implementing `completeStructured` that inspects `req.messages` (the assembled prompt contains the raw diff text verbatim) via regex to extract a value (e.g. the hunk's new-start line from `@@ -X,Y +A,B @@`) and derives its fixture from that — a mutable `phase` flag on the instance then lets a test flip behavior between two sequential batches without per-call fixture wiring. ref: server/src/modules/evals/evals.it.test.ts:65

2026-06-29 — MCP tool functions in `mcp/src/server.ts` are registered as `(args) => toolFn(args)` stubs — all tool functions require `client` as their first argument. The pattern must be `(args) => toolFn(client, args)`. Missing `client` causes the tool to call `client.request()` on undefined and throw at runtime. The bug is invisible at typecheck because the closure captures `client` from outer scope only when passed correctly. ref: mcp/src/server.ts:69

## Codebase Patterns (continued 2026-08-27 — TASK-005)

2026-08-27 — To add a `provider`-aware parameter to two `GitClient` methods (`clonePathFor`, `fetchPullHead`) without touching `RepoRef` itself or any of the ~6 out-of-owned-scope call sites that construct plain `{owner, name}` refs (`ripgrep.ts`, `repo-intel/{service,pipeline/*}.ts`), the widened parameter type is a LOCAL intersection `RepoRef & { provider?: VcsProvider }` declared only at the two method signatures that need it — `provider` is OPTIONAL, so every pre-existing caller passing a plain `RepoRef` (missing the field) remains structurally assignable with zero changes, and every pre-existing implementer of the interface (`MockGitClient`, whose methods declare the narrower plain-`RepoRef` param type) remains a valid implementation too, since a narrower declared parameter type is compatible with a wider-but-optional-field interface requirement. This is the general technique for extending one interface method's input shape in a codebase without cascading the change through every call site. ref: server/src/vendor/shared/adapters.ts:294 (`fetchPullHead`), server/src/adapters/git/simple-git.ts:20 (`VcsRepoRef`).

2026-08-27 — When a required behavior change (PAT must never persist in `.git/config`, AC-005-1) would regress an existing, already-fragile mechanism outside the task's owned paths (here: `sync()`'s hardcoded reliance on `origin`'s stored, credentialed URL — see the Open Questions entry above), the correct scope boundary is to branch the fix by provider inside the OWNED file (`clone()`'s `if (repo.provider === 'azure-devops')` branch in `simple-git.ts`) rather than applying it universally. GitHub's `clone()` path — and therefore `sync()`'s downstream assumption — is left completely untouched; only Azure DevOps (new in this task, no pre-existing working behavior to protect) gets the stricter credential handling. This mirrors the plan's own explicit branching instruction for `clonePathFor` ("if github: unchanged; if azure-devops: new logic") but is a general pattern for any AC that's stricter than what an out-of-scope consumer currently assumes. ref: server/src/adapters/git/simple-git.ts (`clone()`).

## What Doesn't Work (continued 2026-08-27 — TASK-005)

2026-08-27 — The pre-TASK-005 `clone()` created the clone's parent directory via a hardcoded `mkdir(join(cloneDir, repo.owner), {recursive:true})` rather than `mkdir(dirname(clonePathFor(repo)))` — these two happen to be IDENTICAL for GitHub's shallow `<cloneDir>/<owner>/<name>` layout, which is why the bug was invisible for a year of GitHub-only usage. It would have silently broken Azure DevOps's deeper `<cloneDir>/azure-devops/<owner>/<project>/<name>` layout (git clone fails with "could not create leading directories" since only `<cloneDir>/<owner>` — not `.../azure-devops/<owner>/<project>` — would exist). Fixed by switching to `mkdir(dirname(dest))`, which is provably identical to the old expression for every existing GitHub call site and correct for the new deeper ADO path. Lesson: a literal path-construction shortcut that "happens to equal" a more general expression for the only case tested so far is a latent bug waiting for the next case. ref: server/src/adapters/git/simple-git.ts (`cloneInner`).

## What Doesn't Work (continued 2026-08-27 — TASK-006/007)

2026-08-27 — Azure DevOps' `GitApi.getPullRequestIterationChanges(repo, prId, latestIterationId, project, top, skip)` — called WITHOUT an explicit `compareTo` — does NOT return the full cumulative base..head diff for a multi-push PR, despite the SDK's own `.d.ts` docstring claiming "the default value is zero which indicates the comparison is made against the common commit between the source and target branches." Empirically confirmed against the real 9-iteration PR #6327: `compareTo` values of `undefined`, `0`, and `1` returned 7, 7, and 4 files respectively — none matched the PR's true scope. This is NOT actually a bug to work around by preferring a local `git diff` instead: a naive two-dot local diff (`git diff pr-N^1..pr-N^2`) reported 134 files, but that number is a red herring — it also picks up the TARGET branch's own unrelated commits merged in after the PR's branch point (confirmed via `git merge-base pr-N^1 pr-N^2` resolving to a THIRD, older commit, not `pr-N^1` itself). The three-dot diff (`git diff pr-N^1...pr-N^2`, merge-base semantics — same notation the GitHub path already uses) agrees exactly with ADO's 7-file answer. Lesson: `iterations/{id}/changes`'s file list (no `compareTo` needed) was correct all along; don't replace it with a local diff's file list on the assumption that "local git is more authoritative" — only *overlay* patch/stats onto the provider's existing file list by path. ref: server/src/modules/pulls/routes.ts:298

## Recurring Errors & Fixes (continued 2026-08-27 — TASK-006/007)

## Codebase Patterns (continued 2026-08-27 — TASK-006/007)

2026-08-27 — `AzureDevOpsClient`'s constructor takes ONLY the workspace-level PAT — no `baseUrl`/`org` — unlike a naive port of `OctokitGitHubClient`'s single-host pattern. Reason: `Container.vcs(repo)` caches ONE client instance PER PROVIDER (not per repo), but Azure DevOps' `WebApi` connection is scoped to one `{baseUrl}/{org}` at a time, and a single workspace can have ADO repos across different orgs/self-hosted servers. 2026-08-27 — The diff-first merge in the `pulls` detail route is an OVERLAY, not a replacement: `providerDetail.files` (from `VcsClient.getPullRequest()`) stays the authoritative file list; only `patch`/`additions`/`deletions` get overlaid from a locally-computed `git diff`, matched by path.
